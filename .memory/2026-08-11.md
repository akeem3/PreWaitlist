# 2026-08-11 — Story 6.0 Regression Fix (Signup Reroute + Stale localStorage)

## Context

Post-Sprint-1 Issue #15 shipped on 2026-08-10: signup moved to after Step 3. On the
OAuth path (`/onboarding/3` → `/onboarding/signup` → Supabase Google → `/auth/callback`
→ `/onboarding/4`), users were rerouted back to Step 1, and localStorage held stale
data on new onboarding sessions.

## Actual error (from user's devtools)

```
Failed to create waitlist: { code: '23502', message: 'null value in column "subdomain" of relation "waitlists" violates not-null constraint' }
```

POST /api/waitlist returned 400 twice, then the client got `GET /onboarding/1`.

## Root cause (confirmed via web research, not speculation)

`useSyncExternalStore` returns `getServerSnapshot()` during SSR AND during the first
client hydration render. So on a full page load the onboarding context's `rawPersisted`
is `null` and `state` is the empty `initialState` for that first commit:

1. `OAuthFlush` (mounted in `onboarding/layout.tsx`) fired `flushToAPI()` in that same
   mount. `flushToAPI` read context `state` (empty) → `template` defaulted to
   `"minimal"` (truthy), so the empty-data guard `!data.slug && !data.headline &&
!data.template` never tripped → POST sent `subdomain: undefined` → 23502.
2. The `persist(state)` effect simultaneously wrote that empty `initialState` over the
   real Steps 1-3 data in localStorage (hydration clobber).
3. Step 4's "Next" then found no `waitlistId` → `router.replace("/onboarding/1")`.

Second bug: the `completed` flag written by `clearPersisted` was stored INSIDE the
same `prewaitlist_onboarding` object, and the very next `persist` overwrote it away →
next session restored stale completed data.

## Fix applied (src/app/onboarding/context.tsx)

- `flushToAPI` now reads **localStorage directly** via new `readStoredData()` helper,
  layering `overrides` on top — localStorage is authoritative right after a full-page
  load (context state is still empty on first client render). It also hard-requires a
  non-empty `slug` before POSTing (subdomain is NOT NULL).
- New separate `DONE_KEY` (`prewaitlist_onboarding_done`) for the completed marker.
  `persist` only writes `STORAGE_KEY`, so the flag survives until the next session's
  mount effect clears both keys. Mount effect also still handles legacy `completed`
  flag and TTL expiry.
- `persist` is gated: it skips while `persistedState === initialState` (the empty
  hydration snapshot) and there are no overrides, so the hydration clobber can never
  happen. Implemented via reference comparison — NOT a `hasHydrated` state flag,
  because the `react-hooks/set-state-in-effect` ESLint rule rejects `setState` inside
  the mount effect.

## Verification

- `pnpm lint` → 0 errors (2 pre-existing warnings: `brandColor` unused in
  `live-preview.tsx`, `powered-by-footer.tsx`)
- `pnpm build` → success, TypeScript clean, 25 static pages + dynamic routes

## Known limitation (accepted)

Same-SPA-session re-onboarding (complete → immediately start over at /onboarding/1
without a page load, then OAuth again) would have its steps-1-3 storage cleared by the
DONE_KEY mount effect on the redirect. Not reachable in practice: a completed founder
is already signed in, so the signup page auto-flushes and skips OAuth.

# Story 21.4 — Input Validation Audit

**Status:** done
**Epic:** 21 — Full App Scan & Test Case Suite

## Story

As the founder, I want every form and API input probed for validation failures so that the "already failing" hunches are confirmed with evidence before test cases are written.

## Acceptance Criteria (EARS)

- AC1: Every form shall be probed (boundary, malformed, empty, over-length, injection-shaped inputs): signup, signin, forgot/reset password, onboarding 1 (slug/headline), 2 (template), 3 (brand color, logo URL, CTA, milestone thresholds), 4 (decision), 4a (question builder: types, options, caps), 5 (email customisation), public email capture (email format, honeypot, timing, rate limit, consent line, phone E.164, qual answers), subscriber detail PATCH (display_name ≤100), settings (profile, waitlist fields, phone mode), broadcast (subject ≤200, body ≤10k), updates (min-10, body type), waitlist POST/PATCH (slug, milestone rewards validation).
- AC2: Every API route's validation branch shall be checked: 400s with honest error strings, ordering of guards (honeypot → timing → consent → email → rate limit → tier → referral → qual → cap — Phase 6 contract), no raw-error echo to clients.
- AC3: Each probe result shall be recorded: pass / fail-with-evidence (request + actual response vs expected from 21.3 sources) / not-applicable.
- AC4: Failures shall be grouped by severity (broken = accepts invalid or crashes; weak = accepts invalid but harmless; strict = rejects valid input) — the founder-approval list for 21.5.
- AC5: Lint and build shall pass.

## Tasks

- T1 (AC1) Form probes (manual + curl/httpie against local API)
- T2 (AC2) API validation-branch walkthrough
- T3 (AC3-AC4) Results + severity grouping
- T4 (AC5) Gates

## Out of Scope

- Fixing anything; security penetration testing beyond input validation; load testing.

## Dev Notes

- Methods: read the validation code in each route (cheap first pass), then verify the top-risk ones live (local dev server + curl). Highest-risk: slug validation + race, milestone reward thresholds (client `validateMilestoneRewards` + server), question builder caps (Free=2/Pro=5), broadcast/update length caps, phone E.164, unsubscribe HMAC tokens.
- Existing validation inventory is good: Phase 6.4/6.8 established strict ordering; Story 14.4 RFC4180; 12.2.13 display_name cap (audit F1); step-3 milestone client validation (milestone hardening F3/F4). Expect PASS on most — this audit is evidence-collection, not re-design.
- Output feeds 21.5's "Input validation" section directly: failures become pre-flagged test cases (AC4 grouping = case priority).
- Do NOT fix failures here — 21.6 owns fixes after founder approves the list (21.5 gate).

### AC2 — Guard-order walkthrough (`POST /api/subscribers`)

Actual order in `subscribers/route.ts:447-703`: **required → honeypot → timing (≥2s) → email format → display_name ≤100 → rate-limit 5/hr → tier/cap-read (fail-closed) → phone_mode → referral resolve → qual key-filter (fail-closed) → atomic cap claim → insert**. Story text order (`honeypot → timing → consent → …`) is stale: consent guard removed by Epic 18 W3 (code comments confirm), and `display_name`/`phone`/`cap-read` interleave between email and referral. **Informational mismatch — code governs** (per story Risk note). All 400s honest except anti-enumeration generics (honeypot/timing/rate-limit/cap-fail — intentional). No raw echo on any public path (19.4 H9 pattern).

### AC4 — Severity grouping (founder-approval list for 21.5)

**Broken (accepts invalid or crashes): none found.**

**Weak (accepts invalid but harmless, or hardening-grade):**

- **W1** — No slug-format validation: `check-slug` reports `ABC DEF!!` available (live); `POST /api/waitlist` inserts `subdomain` raw, only backstop is 409 on collision. Client normalizes in-flow; direct-API misuse only.
- **W2** — Reserved slugs return `available:false` → client renders "Already taken" (misleading; should say reserved/unavailable).
- **W3** — Broadcast `segment` unvalidated: any typo/missing value silently targets ALL subscribers instead of 400.
- **W4** — Subscriber PATCH `display_name` writable by anyone holding the `(id, referral_code)` pair (in the subscriber's own thank-you URL); no auth, no rate limit. Self-healing (re-settable), display-name only.
- **W5** — Signin/forgot-password stale-state `emailError`: first-submit invalid email skips client validation, fails closed at Supabase (wasted call, generic error).
- **W6** — Unsubscribe page GET mutates `unsubscribed_at`: prefetchers/link-scanners can silently unsubscribe; recovery via resubscribe exists.
- **W7** — Raw `error.message` echo to client: `webhooks/paddle/route.ts:93,132,176,217,254,280` (Paddle infra only — signature-gated), `waitlist/domains/route.ts:60-63`, `waitlist/domains/verify/route.ts:34-36,43-45` (authed founder). Info disclosure, low exploitability.
- **W8** — No server whitelist / no length caps on founder-text passthrough: `template` (degrades to minimal, no crash — verified `template ===` checks), `qualification_enabled`, `headline`, `subheadline`, `brand_color` (client hex-check only), `logo_url`, `cta_text`, `signup_counter_threshold` (client `>0` only, no upper cap). All inserted/updated raw (`waitlist/route.ts:216-235` insert, PATCH `...updates` straight to `.update()`); only failure mode is DB-level. Founder-authed writes only — worst case is the founder's own page/data.

**Strict (rejects valid input): none found.** Email regexes standard-permissive; phone E.164 `+[1-9]d{6,14}`; boundary comparisons are strictly-greater (`>`, so exact-cap passes — code-verified for 200/10k/2000/10; exact-100 `display_name` additionally test-locked in `subscribers-id.test.ts:146`).

**Not-applicable:** load testing (out of scope); authed-route live probes (no founder session — `code+test` evidence substituted and labeled).
